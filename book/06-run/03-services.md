## Когда микросервисов сотни

А что, если веб-проект у тебя — это не один фронтенд и один бэкенд? Трендом последних пятнадцати лет было распиливание монолита на микросервисы. У нас в Ситидрайве, например, было 200 микросервисов, а в Авито и в Озоне их уже тысячи.

::: note cat
Авито в 2024 году рассказывал, что у них работает несколько тысяч микросервисов — [highload.ru](https://highload.ru/moscow/2024/abstracts/13640), а Озон ещё в 2022 году — что у них «порядка 4000 разработчиков и более 3500 сервисов» — [habr.com](https://habr.com/ru/companies/ozontech/articles/708274/)
:::

::: note sparrow
Это что, под каждую ветку поднимать копию всех двухсот сервисов?
:::

И вот когда ты делаешь фичу, ради которой нужно поправить десять микросервисов, совсем легко ошибиться живому человеку, а агенту и подавно. Одно дело, когда сервисов пара, — их можно поднять у себя через Docker Compose, и совсем другое, когда их сотни. Тогда поднимать под каждую ветку превью-стенд со всем проектом, как в прошлом разделе, выйдет слишком долго и дорого.

Скорее всего, в вашей компании уже есть общий **стейдж** — окружение перед продакшеном, где подняты все сервисы из `main`. И вот идея — выкатывать на превью-стенд только те сервисы, которые ты изменил, из твоих веток, а когда им нужно сходить в любой неизменённый сервис, они просто ходят в этот стейдж. Вот работу с такими превью-стендами и нужно автоматизировать для агента, чтобы одной командой он мог поднять ветку своего сервиса и ветки соседних сервисов, которые он поправил, и прогнать фичу целиком.

Запрос с превью-стенда может пройти через несколько сервисов стейджа, и важно, чтобы по дороге он снова попадал в сервисы из твоих веток, а не в их версии из `main`. Для этого запросы к превью-стенду помечают, например, особым заголовком, и каждый сервис, получив такой запрос, передаёт эту метку дальше по цепочке.

Тестовые данные у разных превью-стендов тоже придётся развести, чтобы два стенда не портили друг другу базу. А сами превью-стенды удаляют, например, через пару дней после merge ветки.

::: idea Как это устроено у других
- **Uber** называет такое временное окружение SLATE и выкатывает туда только проверяемые сервисы, а за всеми зависимостями они по умолчанию ходят в настоящие сервисы на продакшене. Удаляется оно само, по умолчанию через два дня — [uber.com](https://www.uber.com/blog/simplifying-developer-testing-through-slate)
- **Signadot** продаёт такие окружения как готовый продукт, и у него есть MCP-сервер, через который их может поднимать сам агент — [signadot.com](https://www.signadot.com/docs/overview)
- **mirrord** подключает сервис, запущенный у тебя на компьютере, к общему кластеру, и для Claude Code у него есть плагин — агент правит сервис у тебя на компьютере, а запросы из него идут в настоящие сервисы кластера — [metalbear.com](https://metalbear.com/mirrord/docs/use-cases/using-mirrord-with-ai/claude-code)
:::
