## Хуки

Тесты и линтеры работают только тогда, когда их кто-то запускает. Можно, конечно, написать в `AGENTS.md`, чтобы агент гонял линтер после каждой правки, и чаще всего он так и будет делать. Но, как мы уже поняли, всё, что написано в `AGENTS.md`, для него просьба, а не гарантия. Поэтому, если проверка должна выполняться всегда, её делают хуком.

**Хук** (hook — от английского «крючок») — это действие, которое Claude Code сам выполняет в определённый момент своей работы, хочет того модель или нет. Событий, на которые можно повесить хук, у Claude Code больше тридцати. Например, хук может сработать перед тем, как агент прочитает файл, запустит команду или поправит код, или сразу после этого. А ещё он может сработать в начале сессии или тогда, когда агент собирается закончить работу. Хуки прописываются в файле настроек `.claude/settings.json` в репозитории, и для каждого указывается событие, на которое он срабатывает, и что именно нужно выполнить. Чаще всего это команда в терминале, но хуком может быть и HTTP-запрос, и вызов тула MCP-сервера, и даже отдельный запрос к модели.

::: note cat
Полный список событий, на которые можно повесить хук, и всё, что хук может вернуть, есть в документации Claude Code — [code.claude.com](https://code.claude.com/docs/en/hooks)
:::

Когда хук отработал, Claude Code смотрит, с каким кодом выхода он завершился. Код 0 значит, что всё в порядке. А если хук завершился с кодом 2, то, в зависимости от события, Claude Code либо не даст агенту выполнить действие, либо покажет ему текст, который хук написал в поток ошибок (stderr). Хуки, которые запрещают агенту что-то делать, мы разберём в главе о безопасности, а здесь нам нужны те, что сообщают ему об ошибках.

::: note cat
В документации Claude Code так и сказано: инструкции агент воспринимает как советы, а хук выполняется всегда — [code.claude.com](https://code.claude.com/docs/en/best-practices)
:::

Начать проще всего с хука, который после каждой правки файла запускает форматтер и линтер только на этот файл. Если всё чисто, он ничего не пишет, а если линтер нашёл ошибки, хук пишет их в stderr и завершается с кодом 2. Так агент узнаёт об ошибке сразу после правки этого файла, пока ещё помнит, что и зачем делал, и тут же её исправит.

Удобство такого хука в том, что линтер в нём проверяет не весь проект, а один файл, поэтому проверка проходит быстро, и агенту не приходится долго ждать её после каждой правки.

Ниже пример того, как в документации выглядит самый простой такой хук. Он только прогоняет форматтер Prettier по каждому изменённому файлу и ничего агенту не говорит. А чтобы хук ещё и сообщал об ошибках, к нему добавляют линтер, который пишет их в stderr и выходит с кодом 2. Собрать такой хук под твой стек проще всего промптом, он будет в конце раздела.

```file title=".claude/settings.json"
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

### Git-хук перед коммитом

Второй вид хуков, который мы возьмём на вооружение, — это хуки уже самого git. Нам нужен тот, который git запускает перед каждым `git commit`, и в нём стоит прогонять хотя бы линтер и проверку типов по изменённым файлам. Так как мы хотим отдать агенту весь процесс целиком, то и коммитить будет тоже агент. Он вызовет `git commit`, git запустит наш хук, хук вернёт ошибку, агент её получит, поправит и снова запустит `git commit`. Поэтому об ошибке мы узнаем ещё локально, а не тогда, когда упадёт CI.

::: note cat
Если команда упала, Claude Code отдаёт агенту её вывод. А если вывод длиннее примерно десяти тысяч символов, агент получит только его начало и конец, а середина будет пропущена — [code.claude.com](https://code.claude.com/docs/en/tools-reference)
:::

Писать такой хук с нуля не нужно, для этого есть готовые инструменты — pre-commit, lefthook, а для проектов на Node.js ещё и husky, который ставится одной командой `npx husky init`. Только не пытайся прогнать на коммите все тесты проекта. Когда их тысячи, коммит будет идти по несколько минут, и разработчики начнут пытаться обходить этот хук, так что на коммите проверяй только изменённые файлы.

```prompt who=cat title="Хук после правки и хук на коммит" note="-"
Настрой две проверки, которые будут сами показывать агенту его ошибки.
1. Хук Claude Code в .claude/settings.json: после каждой правки файла запускать форматтер и линтер только на этот файл. Если нашлись ошибки, отдать их вывод агенту; если всё чисто, ничего не печатать.
2. Git-хук перед коммитом: линтер и проверка типов только по изменённым файлам, чтобы коммит занимал секунды. Используй то, что в проекте уже есть, а если ничего нет — подходящий стеку инструмент.
Проверь оба: сделай правку с ошибкой и убедись, что хук её показал; попробуй закоммитить файл с ошибкой и убедись, что коммит не прошёл. Проверочные изменения потом откати.
Добавь в AGENTS.md: коммитим без --no-verify; если хук упал, исправляем ошибку и коммитим снова.
```

::: note caterpillar
А если агент возьмёт и закоммитит с `--no-verify`?
:::

Флаг `--no-verify` отключает при коммите git-хуки pre-commit, то есть наш хук перед коммитом, и commit-msg. Конечно, можно добавить в `AGENTS.md` строчку о том, что так делать нельзя. Но, как мы помним, для агента это всего лишь просьба, и он может её не учесть. Можно и запретить этот флаг в настройках разрешений Claude Code, но тогда нужно указать конкретную команду, которую мы запрещаем. А записать такую команду git можно десятками способов, ведь флаг ставят в разные места команды, и все варианты не учтёшь. Выходит, что локальные хуки — это вспомогательная быстрая обратная связь для агента, а железобетонная проверка должна проходить в CI.

::: note cat
Правила разрешений, которые пытаются ограничить аргументы команды, в документации так и названы — «fragile» — [code.claude.com](https://code.claude.com/docs/en/permissions)
:::
