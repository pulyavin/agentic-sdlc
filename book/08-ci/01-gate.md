## Нельзя смержить без зелёного CI

Важно, чтобы пул-реквест нельзя было смержить, если упала хотя бы одна проверка. Для этого включи в настройках репозитория запрет на merge, пока все они не пройдут:

- в GitHub — в настройках репозитория, в разделе Rules, в подразделе Rulesets, создай для ветки main набор правил (New branch ruleset), переведи его в статус Active, включи в нём «Require status checks to pass before merging» и выбери, какие проверки обязательны;
- в GitLab — в настройках мерж-реквестов включи «Pipelines must succeed».

Проверки, без которых пул-реквест нельзя смержить, называют **обязательными проверками** (required status checks). Пока хоть одна такая проверка не прошла, кнопка merge неактивна.

::: note cat
Раньше то же самое настраивали правилом branch protection в разделе Branches. Оно работает и сейчас, но в rulesets на одну ветку можно повесить несколько наборов правил. И то и другое в приватных репозиториях GitHub есть начиная с тарифов Pro и Team, а на бесплатном тарифе — только в публичных. «Pipelines must succeed» в GitLab есть на всех тарифах — [docs.github.com](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets), [docs.gitlab.com](https://docs.gitlab.com/user/project/merge_requests/auto_merge/)
:::

Пайплайн в GitLab — это все CI-задачи, которые запустились на мерж-реквест, и если упала хоть одна задача, упал и весь пайплайн. Исключение — задачи с пометкой `allow_failure: true`: они могут падать, а пайплайн всё равно останется зелёным. Поэтому в GitLab этой одной настройки достаточно, если ни на одной задаче нет такой пометки.

В GitHub же каждая CI-задача показывается в пул-реквесте отдельной проверкой, и обязательными нужно отметить конкретные проверки по их названию, а это может приводить к двум частым проблемам:

- Допустим, тесты фронтенда лежат в отдельном workflow (так в GitHub Actions называется файл со сценарием CI), и этот workflow запускается, только когда в пул-реквесте меняются файлы фронтенда. Ты сделал его проверку обязательной. А потом агент присылает пул-реквест, в котором поменял только бэкенд. Workflow фронтенда не запускается, его проверка так и не получает результата и висит в статусе ожидания (Pending). GitHub не даёт смержить пул-реквест, пока обязательная проверка не прошла, так что этот пул-реквест застрянет навсегда, хотя ничего не сломано.
- Бывает, что одна CI-задача зависит от другой, например тесты запускаются только после сборки. Если сборка упала, тесты не запускаются вовсе и получают статус «пропущено» (skipped). А пропущенную обязательную проверку GitHub считает пройденной, и пул-реквест можно смержить, хотя сборка упала.

Поэтому проще собрать все CI-задачи в одном workflow, который запускается на каждый пул-реквест, и добавить в него одну **итоговую проверку**. Она запускается всегда, смотрит на результаты всех остальных и падает, если упала хоть одна. Обязательной в настройках сделай только её.

```yaml title=".github/workflows/ci.yml"
on: [pull_request, merge_group]

jobs:
  # здесь твои задачи: build, lint, unit, integration, e2e
  gate:
    if: always()
    needs: [build, lint, unit, integration, e2e]
    runs-on: ubuntu-latest
    steps:
      - name: Проверить, что все задачи прошли
        if: contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled')
        run: exit 1
```

::: note cat
Так советует и сама документация GitHub — не делать обязательными проверки, которые запускаются не на каждый пул-реквест, а для проверок, которые зависят от других, использовать `always()` вместе с `needs` — [docs.github.com](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)
:::

В `needs` перечисли все CI-задачи без исключения. Если, например, забыть там сборку, то, когда она упадёт, тесты получат статус «пропущено», итоговая проверка увидит только их и пропустит пул-реквест. А `always()` заставит итоговую проверку запуститься, даже если какая-то из задач упала. В списке обязательных проверок она появится под именем `gate`. Событие `merge_group` нужно для merge queue (о ней — в следующем разделе).

### Как не дать агенту обойти проверки

Когда агенту нужно, чтобы CI позеленел, у него всегда есть короткий путь — ослабить саму проверку. Например, снизить порог покрытия, дописать к команде в CI `|| true`, чтобы она никогда не падала, или поправить сам конфиг CI. В прошлой главе мы записали в `AGENTS.md` правило не удалять, не пропускать и не ослаблять тесты, но в очередной раз вспомним, что для агента это всего лишь просьба, и он может её не выполнить. Поэтому не дать агенту схитрить нужно настройками, и тут есть несколько подходов:

- назначь владельцев для конфигов CI, тестов и линтеров в файле `CODEOWNERS` и включи в ruleset правило «Require a pull request before merging» с обязательным аппрувом владельцев кода, тогда пул-реквест, который меняет эти файлы, нельзя смержить без аппрува владельца на код-ревью;
- не добавляй никого в Bypass list в ruleset — это список тех, кому можно обходить правила. Если добавить туда администраторов, агент, который работает с твоими правами, сможет смержить пул-реквест с красными проверками;
- в настройках Claude Code, в файле `.claude/settings.json`, добавь правило, чтобы файлы в `.github/` агент правил только с твоего подтверждения.

Для конфигов CI и проверок обязательный аппрув владельцев — это минимум. А как сделать его обязательным и для кода других команд, чтобы команды при этом не блокировали друг друга, я расскажу в следующей главе.

::: note cat
В GitLab владельцы кода из `CODEOWNERS` есть начиная с тарифа Premium — [docs.gitlab.com](https://docs.gitlab.com/user/project/codeowners/)
:::

```prompt who=cat title="Обязательные проверки" note="Настройки репозитория включай сам, а не через агента"
Посмотри, какие проверки у нас запускаются в CI.
1. Собери их в одном workflow, который запускается на каждый пул-реквест, и добавь итоговую проверку gate: она запускается всегда, ждёт все остальные CI-задачи и падает, если хоть одна упала или была отменена.
2. Напиши, что именно мне включить в настройках GitHub или GitLab, чтобы пул-реквест нельзя было смержить в main, пока gate не зелёный, и чтобы это правило не обходили администраторы.
3. Добавь в CODEOWNERS владельца для .github/, конфигов тестов и линтеров и для самого CODEOWNERS, а кого назначить, спроси у меня.
4. Настрой .claude/settings.json так, чтобы файлы в .github/ ты правил только с моего подтверждения.
Покажи изменения до коммита.
```

::: note caterpillar
А если агент добавит в сообщение коммита `[skip ci]`?
:::

В GitHub Actions есть системная пометка `[skip ci]`, и если написать её в сообщении коммита, CI для этого коммита не запустится. Только обязательная проверка тогда тоже не получит результата и будет висеть в статусе ожидания, так что пул-реквест всё равно не смержить. В GitLab так же: при включённом «Pipelines must succeed» мерж-реквест с пропущенным пайплайном смержить нельзя.
