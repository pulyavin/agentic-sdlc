## Что проверять в CI

Я рекомендую настраивать на уровне CI все проверки, которые только можно. Это тесты всех видов — юнит-тесты, интеграционные, end-to-end, тесты миграций, а ещё линтеры и проверка типов. Мы разобрали их в двух прошлых главах.

Но кроме них есть ещё целый ряд проверок безопасности. Например, проверка кода на SQL-инъекции, поиск паролей и ключей, которые случайно попали в код, и проверка библиотек, которые подключает проект. Для каждой такой проверки есть свои инструменты. Одни ты сам подключаешь в свой CI и запускаешь отдельной CI-задачей, а другие уже встроены в GitHub и GitLab, и их можно просто включить в настройках.

Проверку кода на уязвимости называют **статическим анализом безопасности** (static application security testing, SAST) — это когда инструмент читает код, не запуская его, и ищет в нём опасные места.

| Проверка | На что проверяет | Подключаешь в CI сам | Встроено в GitHub и GitLab |
|---|---|---|---|
| Анализ кода (SAST) | нет ли в коде SQL-инъекций и других уязвимостей | Semgrep | CodeQL, GitLab SAST |
| Секреты | не попали ли в код пароли, токены и ключи | gitleaks, TruffleHog | secret scanning, secret detection |
| Зависимости | нет ли известных уязвимостей в тех версиях библиотек, которые подключает проект | OSV-Scanner | dependency review, dependency scanning |
| Новые пакеты | существует ли пакет, который добавил агент, и не вредоносный ли он | Socket | — |
| Инфраструктура и образы | нет ли в описании инфраструктуры ресурсов, открытых наружу, а в Docker-образах — уязвимостей | Checkov, Trivy | IaC scanning, container scanning (оба в GitLab) |
| Лицензии | подходит ли проекту лицензия новых библиотек | ScanCode | dependency review, license scanning (GitLab) |

::: say cat
В GitHub встроенные проверки бесплатны для публичных репозиториев, а для приватных их можно докупить только на тарифах Team и Enterprise. На октябрь 2026 года поиск секретов стоит $19, анализ кода и проверка зависимостей — $30 в месяц за каждого, кто коммитит. В GitLab найденные уязвимости прямо в мерж-реквесте и проверка лицензий есть только на тарифе Ultimate — [github.com](https://github.com/security/plans), [docs.gitlab.com](https://docs.gitlab.com/user/application_security/sast/)
:::

Особенно внимательно стоит проверять библиотеки, которые добавляет агент. Модели иногда выдумывают пакеты, которых не существует, а злоумышленник может зарегистрировать пакет под таким именем и положить в него вредоносный код. Поэтому проверка новых зависимостей должна смотреть не только на уязвимые версии, но и на то, существует ли пакет вообще и не вредоносный ли он.

::: note cat
В исследовании, которое представили на конференции USENIX Security в 2025 году, шестнадцать моделей сгенерировали 576 тысяч примеров кода, и у коммерческих моделей выдуманными оказались в среднем не меньше 5,2% пакетов, а у открытых — 21,7% — [arxiv.org](https://arxiv.org/abs/2406.10279)
:::

Важно помнить, что сам сканер — тоже чужой код. Сторонние инструменты в CI обычно подключают готовыми шагами — actions — по номеру версии, например `@v2`. Только `@v2` — это git-тег, а автор action может в любой момент переставить тег на другой коммит. Так в марте 2026 года и взломали популярный сканер Trivy. Злоумышленники с украденными доступами переставили теги его action на коммит с вредоносным кодом, который крадёт секреты из CI, и выпустили заражённую версию самого сканера.

Поэтому сторонние actions стоит подключать не по номеру версии, а по хешу конкретного коммита, ведь его подменить уже нельзя. А в GitHub для этого появился ещё и свой lock-файл для actions — примерно как `package-lock.json`, в котором npm в проектах на Node.js закрепляет точные версии всех библиотек. В lock-файле GitHub закреплены не только сами actions, но и всё, что они подключают внутри себя.

::: note cat
Пострадали даже те, кто подключил action Trivy по хешу старого коммита, потому что внутри он сам подключал другие actions по номеру версии. А lock-файл в GitHub пока в публичном превью — [github.com](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23), [docs.github.com](https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles)
:::

Только не спеши сразу делать сканер в CI обязательным. Первый запуск на старом коде обычно находит много уязвимостей и подозрительных мест, и если CI сразу станет красным у всех, разработчики будут пытаться его обойти. Поэтому сначала попроси агента разобрать всё, что нашёл сканер, и поправить, и только потом делай проверку обязательной. И я не рекомендую глушить находки комментариями в коде вроде `# nosemgrep`, чтобы разобраться с ними потом. Агент любит копировать код и начнёт делать так же, и тогда в такой проверке просто не будет смысла.

```prompt who=cat title="Проверки безопасности в CI" note="-"
Добавь в CI проверки безопасности: поиск секретов, проверку новых зависимостей на уязвимости и на то, что пакет существует и не вредоносный, и статический анализ кода.
Выбери инструменты, которые бесплатны для нашего репозитория и подходят нашему стеку и платформе, GitHub или GitLab. Сторонние actions подключай по хешу коммита, а не по номеру версии.
Прогони проверки на текущем коде, сгруппируй находки и исправь их. Если считаешь находку ложной, спроси меня. Если я соглашусь, добавь её в файл исключений сканера с причиной, а не отключай комментарием в коде.
Добавь проверки в needs итоговой проверки gate, только когда они проходят на текущем коде.
```

::: note sparrow
А агент, который читает код и пишет замечания, — это тоже проверка?
:::

Кроме сканеров, в CI обязательно нужно ставить и агентов-ревьюеров, которые читают код пул-реквеста и оставляют к нему замечания. Как их подключить и как вообще теперь устроено ревью, разберём в следующей главе.
